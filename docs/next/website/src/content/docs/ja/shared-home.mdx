---
title: 共有ホームディレクトリ
description: NFS などで 1 つのホームディレクトリを共有する複数のホストで、ソケットやセッションを互いに上書きせずに Herdr を動かします。
---

同じ `$HOME` をマウントする 2 台のホストからは、同じ Herdr のファイルが見えます。設定は共有できます。実行中のサーバーのソケット、保存済みセッション、ログは共有できません。2 台のサーバーが書き込むと、同じソケットパスにバインドし、同じ `session.json` を上書きしてしまいます。各ホストで Herdr を起動する前に、そのホスト専用のランタイム状態ディレクトリを用意してください。

## 共有されるものとホストごとのもの

| ファイル | 場所 | 共有 |
| --- | --- | --- |
| `config.toml`、`plugins/`、`plugins.json` | 設定ディレクトリ: `$XDG_CONFIG_HOME/herdr`、なければ `~/.config/herdr` (`src/config/io.rs` の `config_dir()`) | する |
| `herdr.sock`、`herdr-client.sock`、`session.json`、`session-history.json`、`session-snapshots/`、ログ、`herdr.lock` | ランタイム状態ディレクトリ (`src/config/io.rs` の `runtime_dir()`。`src/session.rs` の `data_dir_for()` が使用) | マーカーか専用の `XDG_STATE_HOME` があればホストごと |
| 名前付きセッション | ランタイム状態ディレクトリ内の `sessions/<name>/` | 上と同じ |
| 保存済みマシン、クライアント設定、エージェント検出の更新 | 状態ディレクトリ: `$XDG_STATE_HOME/herdr`、なければ `~/.local/state/herdr` (`src/config/io.rs` の `state_dir()`) | する。ただしホストごとに `XDG_STATE_HOME` が異なる場合を除く |
| ワークツリーのチェックアウト | `[worktrees] directory`、デフォルトは `~/.herdr/worktrees` | する (意図的な仕様)。共有リポジトリが各チェックアウトを絶対パスで記録するため |

ランタイム状態ディレクトリは次の順で決まります:

1. `XDG_STATE_HOME` が設定されている場合: `$XDG_STATE_HOME/herdr` をそのまま使います。
2. `/var/tmp/herdr-node-id` にノードマーカーがある場合 (Linux と macOS): `~/.local/state/herdr/nodes/<id>`。
3. どちらもない場合: 設定ディレクトリ。これはこれまでのバージョンと同じ挙動で、`$HOME` を共有する 2 台のホストはランタイム状態も共有します。

`HERDR_SOCKET_PATH` は引き続きソケットパスを上書きし、`--session <name>` は引き続き `sessions/<name>` を選びます。

## 各ホストを設定する

ホームを共有するホストはホスト名も同じことがあるため、Herdr がホスト名を勝手に作ることはありません。たとえば、ある JupyterHub ユーザーの pod はすべて `jupyter-<user>` という名前になることがあります。ノードマーカーで各ホストに自分で名前を付けてください。

1. ホストごとに違う名前を決めます。使える文字は `A-Z`、`a-z`、`0-9`、`.`、`_`、`-` です。
2. 各ホストでその名前をマーカーに書き込みます。マーカーは共有ホームの外の `/var/tmp` に置かれます:

   ```sh
   echo ldev > /var/tmp/herdr-node-id
   ```

3. そのホストでサーバーを再起動するか、ハンドオフします。Herdr はプロセスの起動時にマーカーを 1 回だけ読みます。

新しい pod やコンテナはマーカーなしで起動します。新しく作るたびに、Herdr を起動する前にもう一度書き込んでください。マーカーがないと、そのホストは共有の設定ディレクトリにフォールバックします。

このために Herdr が必要とする環境変数はほかにありません。`HERDR_SOCKET_PATH` や `XDG_STATE_HOME` を、シェルプロファイルや Claude Code プロジェクトの `.claude/settings.local.json` の `env` など、共有ホーム上のファイルに書かないでください。そのファイルはすべてのホストが読むので、全ホストが同じ値になり、再び状態を共有してしまいます。例外は `XDG_STATE_HOME=/var/tmp/state` のようなノードローカルのパスで、ホストごとに別のディスクを指します。ただし、その状態は pod を作り直すと失われます。

それでも 2 台のホストが 1 つのランタイムディレクトリを使うことになった場合、2 台目のサーバーは起動を拒否し、`herdr.lock` を持っているホストの名前を表示します。ロックと引き継ぎのコマンドについては[ランタイム状態](/ja/docs/configuration/#runtime-state)を参照してください。

### 既存のインストールを移行する

マーカーを作る前から動いていたサーバーは、再起動するまで (ライブハンドオフを含む) ソケットを設定ディレクトリに置き続けます。新しい CLI からもそこで接続できます。マーカーを作った後の最初のコールドスタートで古い `session.json` と `session-history.json` を引き継ぎ、バックアップとして設定ディレクトリに `session.json.adopted-by-<id>` を残します。古いセッションを引き継ぐのは最初に起動したホストだけで、ほかのホストは空の状態で起動します。

## 別のホストを表示する

各ホストはそれぞれ自分のサーバーを動かすので、あるホストの TUI には、別のホストをマシンとして追加するまでそのホストのペインしか表示されません。どちらのホストからでも SSH 経由で追加できます:

```sh
herdr machine add ldev --label ldev
herdr machine add serine --label serine
```

`ldev` と `serine` は SSH 設定にある SSH ターゲットです。保存済みマシンは `BatchMode=yes` で接続するため、両方のホストで鍵認証かエージェント認証が通る必要があります。初回の `machine add` は対話的なターミナルで実行してください。別のホストへの Herdr のインストールや、そこにある互換性のないサーバーの置き換えでは確認を求められます。

接続は次のように解決されます:

- クライアントは `ssh <target>` を実行し、別のホスト上でそのホスト自身の `herdr` を起動します。クライアントがリモートのソケットパスを計算することはありません。別のホストは自分のノードマーカーでソケットを解決するので、そのホストのサーバーが起動する前にマーカーを書き込んでください。
- 別のホストの `herdr` は、`command -v herdr`、次に `~/.local/bin/herdr` といくつかのパッケージマネージャーのパスから探します。ホームを共有していると、両方のホストが同じ `~/.local/bin/herdr` を見つけるので、同じバイナリを実行します。
- 保存済みマシンの一覧は状態ディレクトリにあります (`~/.local/state/herdr/client/endpoints.json`。`src/client/endpoint/catalog.rs` の `catalog_path()` から)。ホームを共有していると両方のホストが同じ一覧を読むので、各ホストには自分自身を指すプロファイルも表示されます。プロファイルの名前変更、無効化、削除は両方のホストに反映されます。Herdr は同じホストを指し返すプロファイルを検出しません。それに接続して動作するかは検証されていないので、別のホストのプロファイルを選んでください。
- `herdr --machine <label> agent list` などの CLI コマンドは、TUI を開かずに保存済みプロファイルを直接使います。

バージョン: アタッチ時に確認するのはエンドポイントのプロトコル世代とサーバーの機能で、バージョン文字列ではありません (`src/remote/attach.rs`、`src/remote/restart_policy.rs`)。ビルドの完全一致が問題になるのは次の 2 か所です:

- ライブハンドオフ (`herdr --remote <target> --handoff`) は、新しいバイナリとバージョンが異なるサーバーを拒否します (`src/server/handoff.rs`)。
- Herdr が別のホストに自分をインストールするときは、クライアントとバージョンが一致するリリースアセットをダウンロードします。フォークやローカルビルドにはそのアセットがないので、`HERDR_REMOTE_BINARY=<path>` でバイナリを渡してください。

すべてのホストを同じビルドにそろえておけば、どちらのケースも避けられます。

## 確認する

両方のホストを再起動した後、各ホストで次を実行します。

マーカーがこのホストの名前になっていて、ホスト間で異なること:

```sh
cat /var/tmp/herdr-node-id
```

セッションディレクトリとソケットが、このホストの ID の `nodes/<id>` の下にあること:

```sh
herdr session list
```

`directory` 列が `~/.config/herdr` ではなく `~/.local/state/herdr/nodes/<id>` になっているはずです。

各ホストのロックにそのホストの名前が入っていること:

```sh
cat ~/.local/state/herdr/nodes/*/herdr.lock
```

ホストのディレクトリごとにロックが 1 つあり、それぞれに固有の `node` が入っているはずです。

共有の設定ディレクトリにライブソケットが残っていないこと。古いサーバーがすべて再起動していれば、何も表示されません:

```sh
ls ~/.config/herdr/herdr.sock ~/.config/herdr/herdr-client.sock 2>/dev/null
```
